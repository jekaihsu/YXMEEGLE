# Backend integration notes

Run from `meegle`: `uvicorn backend.app:app --host 127.0.0.1 --port 8080`.
Tests: `python -m pytest backend/test_backend.py -q`.

## Persistent state and isolation

The `workspaces` JSON row is protected by a PostgreSQL row lock and a version compare-and-swap. SQLite supports local development and the integration suite; production refuses SQLite. Mutation request receipts prevent a repeated request from producing a second workflow transition. A replay returns the current workspace; reuse with a different action payload returns 409.

Each demo browser receives a separate demo workspace. Role switching keeps that workspace. Lark identities join their allowlisted tenant's shared workspace, which starts empty. Demo sessions cannot read production source caches, import sources, query native approvals, or become a Lark identity. Server roles come from `LARK_ROLE_MAP_JSON`; new identities default to member.

Task ownership is inherited from the node until explicitly reassigned. Changing a node's participants updates only inherited active task owners; completed history and explicitly assigned owners remain unchanged. Deadline adjustments, including moving a date earlier, require approval execution once an initial deadline exists, and may never move the deadline before the task start date. Live `approval_submit` returns 503 before any mutation until an actual native submission adapter is configured; saving a draft and reading an existing approval remain available.

Uploaded files are stored outside static assets under a hashed workspace directory. The download endpoint first checks the signed session and the current workspace's file metadata. Files require a persistent volume on deployment. Source tokens are stored only in the server-side `auth_sessions` database, never in browser cookies or API responses; protect database backups as credentials.

## Source configuration

`LARK_SOURCE_TABLES_JSON` is an array of `{name, base_token, table_id, kind, department?}`. Supported kinds are `quote`, `confirmation`, `contract`, `reporting`, `daily`, `cost`. Quote is the report master; confirmation/contract/reporting are the V4 tables. V3 is not a production source for the new workspace.

Each table may provide an explicit `field_names` array. Otherwise the adapter intersects the documented field mapping with live field metadata and requests only those fields. It follows pagination (200 records/page), with `LARK_SOURCE_MAX_PAGES=50` by default. Hitting the configured bound returns `partial`, never a complete-sync claim. An error leaves the last successful cache and workspace intact. Lark business error 1254302 is reported as a Base resource permission failure.

The maximum configurable record bound is 100 pages per table. Each table summary reports `status`, `pages_read`, `page_limit`, and `record_limit`. Missing/repeated pagination cursors, duplicate records across pages, and incomplete field metadata after 20 pages fail explicitly without replacing the previous cache. Optional Lark field `property`, record `fields`, and empty-page `items` may be null; the reader handles these shapes. A missing response `data` object fails explicitly rather than claiming an empty successful sync.

Source IDs include Base, table, and record ID. Formula values such as `[{text: "3.5"}]` are normalized; missing amounts remain null. Work-item grouping uses the actual linked contract record IDs, not a text field that happens to be named unique key. Ambiguous case-code matches are not merged. Quote records create nine nodes with SOP templates; V4 reporting records add execution tasks. Existing manual task dates/owners are preserved. A changed source on a started or manually edited task is marked `source_change_pending` for review.

Daily rows are evidence of activity only. Live V4 metadata was rechecked on 2026-09-25; evidence is in `backend/evidence/`. The V4 indoor work table does **not** have 工作日期-營業額明細 or 營業額組別-明細. Its 工作日期 is read through 所屬成本單 → 內業成本單 (`tblKwSDRg6WaGHYr`), whose 內業組別 is 控制, 圖報A, 圖報B, or 經理. Control is normalized to 控制組; mixed 圖報 teams are classified as 圖資組/報告組 only when the selected V4 reporting work item supplies that category. The original team is retained as `source_department`.

V4 outdoor work has 工作日期-薪資, a formula from its 所屬成本單 → 外業成本單 (`tbl8wRYCUCvbSoJG`) 工作日期. Both formula and cost date are checked; conflicting dates stay unknown. Outdoor teams such as 地形A/水深B are preserved separately from the 外業組 workflow department. Cost joins include Base/table/record identity to prevent collisions. Unknown/ambiguous links do not silently pick a record. No cost amounts, salary, or allowance records are needed for these joins.

A V4 案件編號 may still be the quote code. Daily entries therefore retain `source_case_code` and use the uniquely matched project's engineering code in `case_code`. Explicit confirmation/work-item record links supplement matching. Formula point values use 最終營業額點數 if present and preserve zero. Source links point to the exact Base/table/record. Import results include counts for unmatched projects, unresolved dates, and missing departments; source sync displays those counts while retaining raw source rows for review. There is no automatic task completion or financial calculation in the importer.

The browser-confirmed indoor raw field `可能的確認單工編(若暫無確認單才需填寫)` is projected by the deployment configuration. When formal case values and formal record links are all empty, its complete code may match one unique project after removing whitespace/Unicode format characters only. Suffixes remain significant, ambiguous projects remain unmatched, and unresolved formal references are never overridden. Such evidence carries `match_basis=provisional_case_code`, retains the original `source_case_code`, and uses `mapping_status=provisional_case_code` when date/group are resolved; missing date/group states remain explicit. Sync statistics add `daily_provisional`. This is activity evidence pending source confirmation, not a repaired Lark relationship. Refreshing a fetched daily record first removes its previous mapped evidence, preventing a changed provisional code from leaving stale evidence on the old project. No outdoor provisional field is enabled without verification.

Large responses support standard gzip negotiation with `GZipMiddleware(minimum_size=1000, compresslevel=5)`. Workspace and authenticated source JSON retain the same schema and access checks; clients that request identity encoding receive ordinary JSON.

## OAuth and native approvals

Set LARK_APP_ID, LARK_APP_SECRET, LARK_REDIRECT_URI, LARK_ALLOWED_TENANTS (comma separated), and LARK_ROLE_MAP_JSON (open_id to pm/manager/member). Configure the exact redirect URL in the application console. OAuth checks a browser-bound signed state and consumes a one-time server nonce; the identity and tenant come from the Lark user-info endpoint. The prototype uses a user access token for source reads, not the local CLI credential store. After expiry users sign in again; token refresh is not implemented.

`LARK_OAUTH_SCOPES` is explicitly sent as a space-separated `scope` in the authorization URL. Its minimal default is `bitable:app:readonly`. For Base plus user-visible native approval reads set `LARK_OAUTH_SCOPES=bitable:app:readonly approval:approval:readonly`, and enable both permissions under **user identity** in the app console before publishing the configuration. The server does not request `offline_access`, messages, or approval/Base write permissions. Configure scopes first, then have users sign in again; adding an app-console scope does not retroactively add it to an already issued user token. The token response's granted/requested scope strings are retained only server-side for diagnosis; successful API access is still the verification of effective authorization.

The first company user remains `member` unless explicitly listed in the role map. After an authorized operator signs in, get that new app's verified `user.id` from `/api/session` and configure, for example, `LARK_ROLE_MAP_JSON={"ou_new_app_user":"manager"}`. Restart/redeploy with the new environment: role mapping is applied on every authenticated request, including existing sessions, and removing a mapping revokes its role. Do not reuse an open_id from another app without verification. Roles cannot be selected by the browser, nor obtained by being the first registrant.

`POST /api/approvals/{id}/refresh` accepts `{version, instance_code}`. It reads an existing native Lark approval only, through `GET /open-apis/approval/v4/instances/detail?instance_code=...&locale=zh-TW&user_id_type=open_id`. This is the **user-token** endpoint. The superficially similar `GET /approval/v4/instances/{instance_id}` accepts tenant tokens and is deliberately not used. Optional LARK_CHANGE_APPROVAL_CODE / LARK_EXTENSION_APPROVAL_CODE constrain the response's `definition_code`. Returned external status is separate from the prototype's approval state: without a configured case/scope binding, `lark_binding_verified` stays false and does not authorize execution. No native approval instances, messages, Base writes, or financial settlements are created by this server.

The token-type distinction is verified in the official generated Python SDK: [user detail request](https://raw.githubusercontent.com/larksuite/oapi-sdk-python/v2_main/lark_oapi/api/approval/v4/model/detail_instance_request.py) declares `AccessTokenType.USER`; [tenant get request](https://raw.githubusercontent.com/larksuite/oapi-sdk-python/v2_main/lark_oapi/api/approval/v4/model/get_instance_request.py) declares `AccessTokenType.TENANT`. The [official MCP README](https://github.com/larksuite/lark-openapi-mcp#quick-start) documents explicit OAuth scope selection. The local CLI schema still lists the historical `approval:instance:read` scope; use the permission name actually available and published in the new application console (`approval:approval:readonly`), and verify with a real user-visible instance after OAuth. No live approval read has been reported as passing without that test.

For production set APP_ENV=production, PostgreSQL DATABASE_URL, SESSION_SECRET (32+ characters), DEMO_MODE=false, PUBLIC_ORIGIN, and persistent UPLOAD_DIR. A cloud demo additionally requires DEMO_MODE=true and ALLOW_CLOUD_DEMO=true; it still cannot access live sources via demo identities.

Official API references used: [Lark record list](https://open.larksuite.com/document/server-docs/docs/bitable-v1/app-table-record/list), [native approval instance read](https://open.larksuite.com/document/server-docs/approval-v4/instance/get), [official Lark OAuth endpoint constants](https://github.com/larksuite/cli/blob/main/internal/auth/paths.go). The v1 authorization URL's `app_id` parameter and v2 token exchange were also checked against the workspace's existing functioning supervisor application (`initiatives/supervisor-kit/daily_dashboard/auth.py`). Live OAuth requires application-console callback configuration and has not been represented as passing without that configuration.
