## 1. 目標與交付邊界

目前 Meegle 的大節點過多，細部 SOP、排程與責任分散；報價總表已有的案件和工項資料仍需重複輸入。新系統以獨立 Web 應用提供 Meego 風格的操作介面，把流程濃縮為九大節點，將細項 SOP 放入可排程、可指派、可追蹤的子任務。

核心成果是：主管看得到案件全貌及卡點；同事從我的工作完成自己負責的事項；報價及 V4 已有資料可追溯地帶入；日報成為作業證據；期限與設計變更受控且保留歷史。

| 交付層 | 本版要求 | 邊界 |
| --- | --- | --- |
| 可操作 prototype | 真正透過 API 儲存示範案件、任務、檔案、留言及審批操作 | 示範資料與真實資料隔離，不寫回正式 Base |
| 真實資料驗證 | 以已授權身分唯讀報價、V4 八表，顯示來源及同步時間；V3 僅供現行日報口徑參照 | 登入成功不等於八表 records 及正規化映射已驗收；不做雙向同步 |
| 正式目標 | 公司 Lark 登入、真實審批、可恢復的持久化部署 | 必須通過正式設定與驗收後才啟用 |
| 後續擴充 | Lark 任務完成回寫、請假自動代理、正式金額結算 | 本版保留介面與證據需求，不以模擬按鈕宣稱串接完成 |

不建立通用流程編輯器，也不以節點完成數比例冒充工程實體進度。AI 自動決策不列為第一版核心。

## 2. 業務來源與資料責任

資料方向為「報價總表 → 工程確認單及合約工項 → V4 日報 → 專案流程與呈現」。V3 是現行日報格式及填報習慣的參考；新系統的目標接點為 V4。來源識別、來源版本及同步時間必須保留。

| 資料 | 權威來源或管理位置 | 新系統使用方式 |
| --- | --- | --- |
| 報價、業主、案件、商業工項、預估量與金額 | 報價總表及工程確認單 | 帶入已有值，顯示缺項，不要求重新抄填 |
| 合約作業工項、數量、標準點數、日報 | V4 | 對應案件及工項，提供作業證據與量能依據 |
| V3 日報 | 現行 V3 | 驗證日期、組別、案號、作業內容及點數的實際填法 |
| 九節點與 SOP、排程、責任、流程完成 | 專案應用 | 由有權人員操作，伺服器檢查條件並留存事件 |
| 正式期限及設計變更核准 | Lark 審批及必要確認證據 | 核准結果與核准版本綁定，手動執行後才變更有效狀態 |
| 原始、修正與核定點數 | 各自來源欄位與檢核狀態 | 分欄呈現，不混加、不用空值代替真實零值 |

同名、同案號、同一文字「來源明細唯一鍵」不足以當跨表主鍵。保存來源系統、Base、table、record ID，另存案號、報價編號、工項及版本作業務對應。一個商業合約項次展開多個作業工項時，不重複計入合約收入。案件與支案各自管理流程、責任與交付；日報不自動開新支案。

真實來源快取與示範流程使用不同儲存範圍。同步來源不得改寫使用者操作中的示範案件，也不得將示範檔案、點數、期限或審批回寫 Lark。完整對應及查證日期見 SOURCE_MAPPING.md。

## 3. 九大節點、SOP 與案件工作空間

| 順序 | 大節點 | API key | 節點目的 |
| --- | --- | --- | --- |
| 1 | 業務 | sales | 承接需求及報價資訊 |
| 2 | PM | pm | 確認案件範圍、參與人員與交付安排 |
| 3 | 工程確認 | confirmation | 確認工項、數量、各組工作量及交付依據 |
| 4 | 外業 | field | 安排出工、提交作業及成果 |
| 5 | 控制 | control | 處理外業資料、檢核與提交接續成果 |
| 6 | 圖資 | mapping | 整理圖資及製圖成果 |
| 7 | 報告 | report | 製作及提交報告 |
| 8 | 計價 | pricing | 整理計價交付與相關依據 |
| 9 | 結算 | settlement | 彙整案件結算作業及狀態 |

每個節點建立固定 SOP 範本，主管可增補案件需要的子任務。固定必要任務未完成時，節點不得通過；新增任務可明確標示必要或非必要。正式細部 SOP 與必要完成證據尚未核定，原型須標示「示範條件」並可設定，不能把樣板當正式制度。各案可有多個工項同時處於不同階段，外業與內業可並行，不使用單一「目前節點」覆蓋整案的並行工作。

案件、節點及子任務應呈現工作說明、輸入、輸出、文件、留言與操作歷程。子任務至少包含標題、所屬工項、負責人、開始日、期限、營業額點數、狀態、必要性、修訂版本及實際開始／完成時間。輸入與輸出文字和檔案分別保存，文件區分 input/output 與版本。

前置條件採指定輸入或對應工項成果；不要求整個外業大節點全部完成，才讓控制或其他下游處理已可使用的資料。缺少必要輸入時明確顯示等待原因，不偽造完成。

節點狀態固定為 pending、in_progress、completed、paused、superseded。子任務沿用上述狀態並增加 rework。介面以繁體中文呈現：未開始、進行中、已完成、暫停、已被新版取代、退回補正。節點通過與子任務完成是不同操作。

## 4. 人員、排程、營業額與時間

### 4.1 人員統一設定與繼承

案件的人員設定集中維護各節點負責人與協作者。新建子任務預設繼承節點負責人，節點主管再分派實際執行人。更新節點負責人時，仍使用繼承值的任務跟隨更新；曾個別分派的任務維持原指派，避免無提示改派。

各節點主管安排所屬子任務開始日、期限及工作量，PM 維護跨節點銜接。所有改派留存前後責任人與操作者。一般協作者可依權限補資料及留言，但不能因能編輯案件而取得完成或通過權限。

### 4.2 組日與工作量

使用者已定義「1 營業額＝一組出工一天」，用於量能估計，不是金額。外業以整組計算；內業以一人一組作為原型預設。成本、合約金額、預估營業額與核定點數分開顯示。

V4 工項帶入的預估營業額是該工項工作量總額。SOP 子任務的點數是同一總額的分配，不可在工項、節點及子任務各計一次。新增 SOP 預設未分配；主管可重新分配，畫面顯示來源總額、已分配、未分配與超配。明確零值與未設定不同。

量能視圖按組別及日期顯示可用組日、已排工作量與尚未排定工作量。原型預設一個外業組一工作日可排 1 點；內業一人一天 1 點。請假、支援及非標準配置以明示調整處理，正式容量標準仍待公司核定。

原始日報、修正及核定點數各自保留。日報有同案作業紀錄不代表某項 SOP 已產出可扣抵的點數；尚未可靠對應到子任務時，僅在案件呈現，不自動扣減該子任務剩餘量。人員參與同一工單的完整點數不得跨人相加；公司工單總數及點數需去重。

### 4.3 排程與流程時長

計畫開始日、正式期限、實際開始及完成時間分開保存。負責人按「開始」產生 started_at，按「完成」產生 completed_at。流程時長是開始至完成或目前時間的經過時間，不是日報工時；等待、待審及暫停期間保留在經過時間內，暫停時長另列並顯示原因。逾期天數依公司工作日計算。

工天與日曆工期分開。部門工作量加總不能直接當成案件完工日期。原型工作日預設週一至週五，另提供假日與補班設定；正式使用前由公司提供日曆。日期依 Asia/Taipei，正式部署使用真實現在時間，示範可用固定基準日供重現。

## 5. 日報證據與流程狀態

已確認「隔天處理」是下一工作日開始，並非隔天必須全部完成。外業日報的工作日期 D 觸發下一工作日控制組接續檢查；不用日報上傳時間，也不等整個外業節點結案。

現行日報無法可靠分辨在處理哪一天的外業資料，因此原型以「日期＋控制組＋案號」判斷本案當日是否已有作業紀錄。使用者接受先按案號判斷，不強制工項或批次精準匹配。相同案號與接續日期只產生一項案件層級提醒。

| 日報檢查結果 | 顯示 | 流程效果 |
| --- | --- | --- |
| 有相符日期、組別與案號 | 本案已有作業紀錄，可查看人員及內容 | 不自動完成或開始所有 SOP，不視為整批成果可交接 |
| 查詢成功但無相符紀錄 | 尚未查到作業紀錄 | 供主管追蹤，不直接認定沒有工作 |
| 來源未連線、失敗或過期 | 來源待同步／資料可能未更新 | 不當作零筆作業、不宣告未開工 |

任務實際狀態仍由有效負責人的流程操作決定。控制到圖資、圖資到報告的接續，以指定輸入／成果及排程為依據，不從案號日報推導不可證明的批次完成。保留未來細化批次的來源連結，但不要求同事為原型重填日報。

## 6. 正式期限與展延

正式期限一經建立，任何更改都必須走 Lark 審批，不依變更天數、是否提早或是否內部期限豁免。首次排程可設定期限，保存 original_due_date；既有期限不得透過一般編輯、拖拉或改派繞過審批。

期限提前及延後都屬正式期限調整，新日期不得早於開始日。真實工作區尚未配置可驗證的正式送審 adapter 時，只能保存草稿及唯讀查詢既有審批，送審回 503 且不更動期限、不凍結任務；不因配置審批 definition code 就模擬送出成功。

展延單從選定起始節點帶出受影響任務及後續排程，需填理由與各任務新期限，顯示原期限和原排程，由主管確認。提出、待審或核准未執行期間，原期限仍有效；不因送審自動延長，也不凍結作業。

狀態依序為 draft → pending → approved → executed，另有 rejected、withdrawn。Lark 核准後成為「已核准待執行」，由具權限 PM／主管明確套用核准日期，畫面標示「已展延」；保留原期限、前一有效期限、審批依據與執行人。「已展延」是執行結果標記，不另增任務狀態值。不得把後續推算日期視為已核准，送審內容包含的日期才能套用。

審批版本與目前任務版本不一致、核准已失效、資料缺漏或操作者無權時阻擋執行。改動待審內容須以新草稿重新送審。重送同一執行請求僅生效一次。

## 7. 設計變更、三線確認與版本

設計變更是案件外掛入口，可在任一階段提出。草稿包含理由、變更範圍、受影響工項及任務、目標接續位置、修訂文件，以及費用和排程影響。本文不替公司訂定對外合約或金額核決制度。

| 階段 | 必要行為 |
| --- | --- |
| 草稿 draft | 整理會議紀錄、修訂圖、工項及接續安排，不提前凍結 |
| 送審 pending | 同時啟動業主確認、公司主管確認、Lark 審批三線；立即凍結受影響工項及其下游同工項工作 |
| 三線處理 | 三線並行，互不取代；未受影響工項可繼續 |
| 核准 approved | 三線全部完成才可成為已核准待執行；仍保持凍結 |
| 手動執行 executed | 有權 PM／指定主管核對版本及範圍，手動接到新版和指定位置 |
| 駁回 rejected／撤回 withdrawn | 保留審批歷史，受影響工作不自動恢復；負責人／PM 明確填原因後恢復 |

凍結按 work_item_id 對應範圍及下游辨識，不粗暴暫停整個案件。凍結期間不得完成、通過或使用被凍結成果推進該工項；其他工項照常操作。正式期限不因凍結自動改變；若需調整，核准內容必須包含明確期限與審批依據。

執行時保存舊任務、文件及成果，舊版標示「變更／已被新版取代」即 superseded，另建下一修訂版本的任務。不得刪除舊歷史，亦不得將目標節點自動標為完成。新任務仍由有效負責人滿足條件後完成。

核准不是完成成果的代名詞。執行前檢查三線皆有效、送審內容未變、目前版本相符、操作者被授權；相同 request_id 重複請求不重建新版。已執行變更後若需撤回實質成果，應另提新變更，不回寫抹除既有執行。

本地及明確啟用的雲端 preview 可提供明顯標記的三線模擬操作；正式公司工作區不得提供手動偽造 Lark 核准的途徑。真實 Lark 審批提交 adapter 未設定時，顯示未串接，阻擋正式送審及執行，不先寫成已送審。

## 8. 權限、文件與歷程

公司 Lark 帳號是正式登入入口，以穩定使用者 ID 及公司 tenant 辨識，不以姓名授權。PM、節點主管與一般成員分工明確。節點完成由該節點負責人操作，必要有效任務全部完成且無相關待審變更才能通過；PM 不具無條件強制通過權。

子任務完成僅限當前負責人或明確有效代理，必要輸出不得空白。原型代理採明確種入的有效代理示範；正式自動代理須核對請假審批、實際交接人、有效起迄及撤回狀態後另行啟用，不以預設交接人取得永久代理權。

文件支援上傳與經檢查的 http(s) 來源連結，區分輸入、輸出、節點、版本與上傳人。案件及任務提供可分享的應用連結，收件人仍須登入並通過權限檢查，不是匿名公開分享。下載須經登入授權，不暴露伺服器路徑。輸入、輸出文字及附件不能因改版而遺失。

所有成功寫入產生不可省略的操作事件，包含案號／任務、操作者、行為、時間及前後變更內容。留言保存作者及時間。審批保存提出人、三線確認歷程、送審／執行時間、參考連結、附件及操作歷史。

狀態與權限判斷由伺服器執行。前端按鈕隱藏僅用於提示，不是授權邊界。版本衝突要求重新讀取後確認，不能靜默覆蓋。

## 9. 畫面與操作旅程

視覺與互動參考 Meego：固定側欄、清楚的案件表格及狀態標記、詳情頁籤、節點與子任務、抽屜式詳情及明確的主要操作。所有文案使用繁體中文；使用者看得到來源和狀態，無須理解 API 或資料庫。

| 畫面 | 核心內容 |
| --- | --- |
| 公司駕駛艙 | 案件進度、逾期、待審變更、接續工作提醒、組別工作量，點擊可追到明細 |
| 我的工作 | 分派給我、代理承接、今日及逾期待辦、等待輸入、已完成與退回補正 |
| 案件詳情 | 九節點概覽、工項與 SOP、參與人員、輸入／輸出、文件、留言及歷程 |
| 子任務詳情 | 負責人、排程、期限、組日、說明、前置輸入與成果，開始／完成／退回 |
| 審批中心 | 展延與設計變更、三線狀態、影響範圍、前後排程、核准待執行清單 |
| 資料來源 | 真實唯讀來源、最後同步時間、失敗原因與來源紀錄連結 |

第一條演示旅程：主管發現 A 案控制接續未查到日報 → 點入查看來源 → 控制負責人開始 SOP、補交成果並完成 → 下游查看指定輸入 → 主管確認節點。另一條旅程展示正式期限申請、待審仍依原期限、核准後套用；第三條展示三線並行、局部凍結、手動換版及舊版追溯。

示範資料持久化與重設都必須由 API 完成。畫面不能只改本機狀態而假稱成功；失敗時顯示原因。重設僅管理角色可操作並有明確二次確認，作用範圍只有示範工作區。

## 10. 系統、部署與資料保護

技術架構採 React＋TypeScript 前端、FastAPI 後端、PostgreSQL 資料庫，以同網域 Docker 應用部署於 Zeabur，使用 Zeabur 預設 HTTPS 網域。雲端使用 PostgreSQL 取代 SQLite，prototype 採單實例並接受維護短停。所有流程寫入通過後端；不讓瀏覽器持有 Lark 憑證。資料庫與 /data/uploads 上傳文件使用持久化儲存，備份與恢復涵蓋兩者。

正式公司入口使用 Lark OAuth，驗證 state、公司 tenant 與目前使用者權限，session 使用安全 Cookie。APP_ENV=production 預設 DEMO_MODE=false，缺少正式登入設定不能自動退回 demo。若提供雲端 preview，須明確同時設定 DEMO_MODE=true 與 ALLOW_CLOUD_DEMO=true，只允許隔離示範工作區的角色切換、模擬確認與重設；不代表可偽造正式核准。真實 Base 的唯讀入口仍須有效 Lark 身分，不能用 demo 角色繞過；同步使用最小授權並保存結果及時間。審批送出、事件接收及外部回寫先在 demo 模擬，真實流程另以正式試辦驗收。實際來源設定預設只匯入報價與 V4，V3 保持研究對照用途。

Docker 映像、啟動設定、健康檢查、資料庫初始化、持久化 volume、備份及還原程序需納入技術交付。備份不能只包含程式或快取。系統時間採 UTC 儲存及 Asia/Taipei 顯示；日報業務日期保留本地日期語意。

接口與具體限制見 IMPLEMENTATION_PLAN.md。正式 Lark 審批、代理與來源同步的能力，以實測驗收為準；未設定或未驗證功能必須在 UI 明示。

OAuth 必須明確請求 LARK_OAUTH_SCOPES，預設最小值 bitable:app:readonly；讀既有審批另加 approval:approval:readonly，並確認 App user 權限發版及使用者授權。伺服器依 LARK_ROLE_MAP_JSON 將 open_id 映射 pm／manager／member；未列出的使用者均為 member，首位登入者不自動成為主管。來源同步限制 PM／manager，讀取使用該登入者的 user_access_token，不自動改用 tenant token。

唯讀原生審批使用支援 user token 的 GET /open-apis/approval/v4/instances/detail（instance_code 參數）；/instances/:instance_id 是 tenant token 端點，不可混用。外部 APPROVED 只更新外部查詢結果，不等於本案已核准；尚未綁定申請版本及三線證據前，不能解除凍結或執行變更。

來源 records 每頁 200 筆，每表預設最多 50 頁（LARK_SOURCE_MAX_PAGES，可調至 100 頁）。未讀完標示 partial 及每表頁數／上限，不呈現完整成功；欄位未完整、分頁游標缺漏或重複、重複 record 均明示錯誤，保留上次成功快取。任何來源片段、映射缺漏或過期資料均不能作為「沒有日報」的判定。

## 11. 驗收與正式上線條件

以下是驗收要求，不是已通過的測試結果。

| 編號 | 情境 | 通過條件 |
| --- | --- | --- |
| A01 | 報價／V4 帶入 | 可查看來源與缺項，不重填已有資料，不寫回正式來源 |
| A02 | 九節點及 SOP | 固定任務與新增任務可排程分派，必要任務未完成不能通過 |
| A03 | 人員繼承 | 新任務繼承節點責任；個別改派後不被批次設定覆蓋 |
| A04 | 組日 | 上下層不重算，顯示分配餘額與超配，未知值不當零 |
| A05 | 日報案號證據 | 同案控制日報顯示已有作業，不完成 SOP；失聯不當無作業 |
| A06 | 接續作業 | 已有指定成果可以下游處理，不要求全外業節點完成 |
| A07 | 流程時間 | 起訖及暫停清楚，經過時間與工時分開 |
| A08 | 正式期限 | 編輯、拖拉及 API 不能繞过審批，待審原期限有效 |
| A09 | 展延 | 顯示連動影響，核准後明確執行，未核准日期不變 |
| A10 | 設計變更 | 三線並行全部完成才可執行，送審即局部凍結 |
| A11 | 駁回與換版 | 不自動解凍，手動恢復留原因；舊版可追溯，新版不自動完成 |
| A12 | 權限 | 非負責人不能完成，PM 不能強制通過；明示 cloud demo 仍不能存取真實來源或偽造正式核准 |
| A13 | 一致性 | 同 request_id 僅生效一次，過期 version 回 409 並保留新資料 |
| A14 | 文件與留言 | 重載後仍存在，文件按版本留存，未登入無法下載 |

需要單獨驗收的後續能力包含真實審批事件、請假代理、Lark 任務雙向操作及正式結算。取得資料來源權限，不代表已取得這些外部寫入或通知能力。
