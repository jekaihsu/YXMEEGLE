## 3. 欄位與檔案映射模型

採 PostgreSQL 正規化實體，所有列含 organization_id，外鍵與查詢都帶租戶範圍。原始值可用 JSONB，業務識別與狀態不可僅埋在 workspace JSON。

| 實體 | 主要欄位／約束 |
| --- | --- |
| input_definitions／input_definition_versions | 穩定 key、版本、節點／工項／SOP 適用規則、標題、型別、單位、必填條件、讀寫角色、審批要求、來源證據；已發布版不可改寫 |
| input_instances／input_revisions | project/node/task/work_item、definition_version、草稿值、last_synced_value、local_version、submitter、代理身分、來源版本；每次提交保存不可變意圖 |
| field_write_mappings | connection、Base/table/field ID、型別、目的 record 解析規則、允許操作、transform_version、權限、啟用狀態；伺服器白名單，不接受前端任意 ID |
| write_target_bindings | project/confirmation_version、source_record_id、用途及生效期；同案多來源可多個讀取，但每個可寫語意必須解析唯一目的 record，否則阻擋 |
| input_documents／document_versions | 文件 UUID、案件／工項、Input/Output/佐證、版本、檔名、MIME、大小、SHA-256、上傳者、狀態、前版；附件新版本不覆蓋舊檔 |
| document_links | 文件版本與節點／任務的多對多關係、用途、適用版本；同文件被多任務引用不重複上傳 |
| drive_locations／remote_file_receipts | connection、根目錄／folder token、file token、資源型別、存取範圍、owner 管理策略、核實時間、遠端回執、版本識別 |
| writeback_batches／writeback_steps | batch UUID、Idempotency-Key、意圖 hash、目標快照、狀態、租約、嘗試次數、下一重試、錯誤分類、readback 結果；每個遠端效果一個 step |
| outbox／audit_events | 同一 DB 交易建立草稿提交、預期變更及 job；每次權限核對、送出、讀回、衝突處置、重試、取消都有事件 |

唯一约束至少包含 `(organization, actor, idempotency_key)`、`(batch, step_key)`、`(connection, base, table, record_id)`。同冪等鍵不同意圖回 409，不能當作成功。案件與工項版本都是明確外鍵，並保留確認單編號當時顯示快照。

### 3.2 型別及文件規則

- 文字、選項、數值、日期、人員及關聯分別驗證；Decimal 保存金額與數量，空值與0、清空與未修改分開。選項／人員／關聯值由核定 schema 解析，不接受任意展示文字。
- 日期區分台北業務日期與精確時間；來源 datetime 顯示日期時不可無意移日。對日期格式、單位與時區做 round-trip 測試。
- 公式、lookup、自動編號、系統時間等唯讀欄只讀；影響核准範圍／預算／期限的寫入綁已核准且仍有效的業務版本。
- Drive 檔案與 Base 附件欄不是可直接互換的 token。第一版以 Drive 為檔案保存處，Base 保存合法文件網址／索引；若原欄要求真正附件，查證專用附件流程及 token 相容性後另映射，不能偽造附件 CellValue。
- 目錄提案為「確認單編號／節點／Input」，文件版本由索引與不可變檔名識別。未出確認單先用暫存案件 ID，後續更新關聯；不為改編號任意搬移或重上傳所有檔案。
- 同名檔案不視為同檔，同 hash 也只在同租戶／允許存取範圍與用途內去重；不能讓跨案件引用洩漏文件。已在 Lark 的文件保存引用與權限核實，不強制複製。
- 上傳尺寸／分片／配額依實際 API 與公司規則設限，不在本稿承諾未核實限制。暫存檔加密、限制存活期；遠端確認可讀後才可清理本地暫存，備份保留依核定政策。

## 4. 儲存、衝突與冪等

UI 分為「儲存草稿」「儲存至 Lark」「正式發出」等明確動作。後端先驗證使用者當下的案件／欄位權限、定義版本、record 綁定及核准狀態，保存提交與 outbox，再回傳 batch ID；前端按欄位與文件顯示結果。

### 4.1 狀態與正常順序

`draft → queued → validating → uploading → writing_fields → verifying → succeeded`；分支為 `conflict / partial_success / retry_wait / blocked_auth / outcome_unknown / failed / cancelled`。即使 Base 成功、Drive 失敗也不能顯示整批成功；UI 顯示「欄位已儲存，2 個檔案中 1 個待重試」。

1. worker 取得租約；重新核對操作者仍在職、權限與代理有效期，以及目的 schema／資源存取權。
2. 對同一遠端 record 串行，取目前值，与編輯時基準比較。
3. 上傳新文件至核定位置，保存遠端 token；驗證大小／可讀性及可取得的校驗資料。下載重算 checksum 是否可行及成本在 staging 驗證，不能假稱 API 已回 SHA-256。
4. 只更新白名單中確實修改的欄位與已成功的文件引用；不送整列以免抹掉別人欄位。若任務要求所有文件，缺一不可提交最終完成狀態。
5. 重新讀取欄位及文件 metadata，轉回本地語意比對，保存可稽核回執；通過後才標 `succeeded`。
6. 若是正式發出，另外完成不可重複的發出命令與交接事件；單純回寫成功不發出。跨系統狀態未確定時保留「發出待核實」，不再次交接。

### 4.2 三方比較與外部並發

每欄保存 base_value（開始編輯時）、local_value、remote_value。若 remote==base，可嘗試更新；remote==local，視為目的值已存在但仍須核實回執；remote 和 local 都不同，回衝突。不同欄互不覆寫，可按欄位續存；同欄提供保留遠端／重新編輯，本地覆蓋也必須重新授權及確認最新基準。

不假設 Lark 端點提供 ETag/CAS。實作前查最新官方契約與隔離測試；若無條件寫入，系統內 per-record lock＋寫前讀＋寫後讀只能降低衝突，**不能保證阻止 Lark 原頁使用者在中間同時修改**。一般 Input 採衝突偵測與稽核；關鍵核定金額／期限使用受控流程或專用 staging 欄，未取得可靠核准版本與發布策略前不啟用直接覆寫。

### 4.3 不確定結果與部分成功恢復

| 故障 | 恢復方式 |
| --- | --- |
| DB 已提交、worker未啟動 | outbox/job 輪詢重取；租約過期可續行 |
| Drive 已傳成功、Base 失敗 | 保留 file token 與成功 step，僅重試欄位及引用；不重新上傳、不自動刪檔 |
| Base 成功但回應中斷 | 先 GET 讀回目的欄與提交識別；相等才核實成功，無法判定進 outcome_unknown |
| 檔案上傳／建 record 回應中斷 | 若官方端點可用 client token 先採其契約；否則透過本次 upload UUID、核定目錄索引、大小／hash等證據核對。證據不足停留未知，不盲目重建 |
| 429／暫時網路／5xx | 指數退避+jitter、遵守可用 Retry-After、有限次數，超過轉人工可重試 |
| 401／refresh失败、403、資源不存在 | 停止依賴步驟，保留已成功回執；重新授權／查證資源，不無限重試、不偷換身分 |
| schema 刪除或型別變更 | 相關 mapping停用，顯示欄位契約變動；保留草稿，不能換同名欄重試 |
| 取消時已有外部效果 | 停止尚未執行步驟，標部分已儲存；不聲稱回滾遠端，不自動刪除或覆蓋他人資料 |

遠端「存在」不等於本次寫入成功，可能由別人同時產生；回執記錄證據及判定程度。資料庫冪等能保證本地不重複排程，不等同外部恰好一次。對無可靠幂等的 create/upload採保守未知狀態及人工核對。

## 5. 權限、離職與長期維運

角色採權限能力而非只有一個 admin 開關。案件財務讀取依有效公司內部身分開放，不另要求財務角色或案件承辦資格；寫入、核定、審批則依角色、案件範圍、欄位及動作判斷。行政承辦不自動取得所有財務寫入或核准權。

| 能力 | 建議權限規則 |
| --- | --- |
| 一般 Input 草稿／提交 | 該案件／任務執行者及授權主管；依欄位白名單 |
| 行政公務及計價／請款／入帳／結算／結案承辦 | 行政公務由行政承辦；其餘由 PM 與行政共同同步處理，已確認本批需兩方皆通過才完成 |
| 案件預算／成本明細／毛利及相關附件讀取 | 所有有效公司內部使用者可讀，不需特別財務讀取角色；不因此新增個人 HR／薪資匯入 |
| 計價金額／收款入帳等關鍵欄 | 專用財務操作權＋適用審批／核對条件；不是任意 Input 編輯 |
| 確認單正式發出／PM交接 | 具發出權的承辦者；指定有效PM、核定版本與必要文件通過；PM接手事件冪等 |
| 來源映射、根目錄設定、授權管理 | 系統整合管理權；不因此取得財務寫入、核准或額外個人 HR 資料權限 |
| 代理 | 限定案件、任務、動作及有效期，不擴張財務寫入或審批權；保留實際操作者與被代理人 |

案件財務API、通用來源預覽、搜尋、計數、匯出、附件連結與下載均採相同內部全員可讀規則，拒絕外部、匿名及停權者。Drive原始URL可以绕过工作台，因此遠端檔案也須實現公司內部可讀、對外不開放；不可用「任何有連結者可讀」解決403。讀取與編輯／核准的遠端權限分開，不因內部可讀即給全員編輯權。

應用身分適合可獲准的背景工作，但 app scope、Base資源存取、Drive目錄權限皆需實測；user權限不能轉當bot權限。優先建立公司受控的資源持有與至少兩名管理者，不以建立者個人雲盤或 session 作永久依賴。若目標 API 必須 user 身分，保存 connection owner、允許用途、加密refresh資訊與接替流程；此人離職後不能繼續冒用token。

離職／停權後撤銷 session，停止新操作、分派及未執行job；已在飛行中的請求可能已產生遠端效果，需核實並記錄。隊列必須重新檢查 actor 授權，不因 submit時有效就永久有效。接替者可查看可見範圍的草稿，審閱後以自身名義重新提交／接管剩餘步驟，保留原批次回執，不重做成功上傳。

背景連線不可用時不影響已授權使用者查看現有歷史，但清楚標示資料新鮮度；未確認可寫身份前只能存草稿。管理者交接需核對根目錄、檔案、Base、App管理與worker連線，不僅改工作台負責人姓名。

### 5.1 人員與來源權限後端契約：異動不改 code／env、不重新部署

新人入職、調職、離職、代理及授權異動均透過 PostgreSQL 與管理 UI 維護。環境變數只保存必要部署／金鑰基礎設定，不再用 `LARK_ROLE_MAP_JSON` 作日常人事權限權威；舊配置以一次性可稽核遷移匯入 role_bindings。不得在 SOP 範本硬編人名或 open_id，範本只指定角色／部門責任，實例由分派規則解析有效人員。

主協調本輪查到 Meegle 業務流程角色共十類：總經理、副總經理、專案經理、專案助理、業務經理、行政經理、外業經理、外業組長、內業經理、內業組長。它們作來源角色目錄，不等於已取得公司完整組織；team list 為0不代表公司沒有部門。完整Lark部門及名單尚未取得。職稱不自動映射系統超級管理權，也不自動授予財務寫入／核准權；案件財務讀取依內部身分，不依職稱。

| 資料／管理 API 提案 | 契約 |
| --- | --- |
| people、departments、memberships | 永久person UUID、在職狀態、有效期部門；`POST /admin/people`、`PATCH /admin/people/{id}`、`POST /admin/memberships`，帶物件版本及冪等鍵 |
| external_identities | `(organization, provider, app_id, external_id_type, external_id)` 唯一映射；open_id依App範圍，姓名只展示。重名不自動合併；App換代透過受控對照遷移 |
| roles、role_capabilities、role_bindings | 職務與操作權分開，寫入／核准绑定可限案件／部門／欄位分類、有效期；案件財務讀取由內部有效身分提供。管理UI預覽增減權，授權管理者不能超過自身可授出的能力或繞過財務寫入／核准授權 |
| `POST /admin/people/{id}/suspend` | 同一DB交易停權、提升authz_version、撤銷session、停用有效代理／新分派、記錄audit及job控制事件；回傳未結工作與待交接摘要，不刪歷史 |
| `POST /admin/handovers/preview`、`/commit` | 預覽範圍／新負責人可用性；commit鎖定版本，保留歷史actor，不改已完成任務。無有效接手者轉待分派，不默認分给最高主管 |
| `POST /admin/delegations`、`/revoke` | 明確被代理人、代理人、起訖、案件／動作；代理到期於每次請求檢查，不只靠排程清理 |
| source_connections、resource_grants | 來源identity、Base/table/folder白名單、讀／寫用途、持有人及管理者、credential引用、驗證狀態；UI可維護映射和重授權，憑證不可讀回前端 |
| `POST /admin/source-connections/{id}/verify`、`/reauthorize` | verify唯讀檢查schema／目的資源存取；reauthorize走正式授權，不能讓管理UI自行賦予Lark不存在的權限。遠端App scope或資源grant若需Lark管理者操作，顯示具體待辦，不要求改程式或部署 |

每個後端請求及worker執行前查有效人員／binding，token或session中的role快照不作長期權威；快取鍵包含authz_version且撤權事件使快取失效。停權交易後到達的請求必須拒絕；在飛行中的遠端寫入仍可能成功，按前述回執核實處理，不能承諾跨系統瞬時撤回。

API錯誤分為未登入401、無權403、版本／目的衝突409、內容422、來源授權阻擋及暫時不可用；不得以空列表掩蓋授權失敗。所有管理API保存操作者、理由、前後binding及有效期；帳號重新入職由具權限管理者確認身份，不因同名自動恢復舊權限。

新增驗收：不改code、env或重新部署，透過管理UI完成新增人員→授案件／節點角色→分派→調職撤舊寫入範圍→限期代理→停權→交接；API及背景job權限立即依DB生效，既有歷史不遺失。另驗證有效內部新人可直接讀案件財務但不自動獲寫入／核准權、同名不同人不共用身份、十類來源職稱均不自動成為系統管理員，以及來源連線管理者離職後由另一有效管理者續接。

### 5.2 節點共同處理與審核規則

使用者已決定計價、請款、入帳、結算、結案由 PM 與行政共同同步處理，且本批預設為 **PM 與行政兩方都通過才完成**。每個節點仍可設定 `all`（指定人全數通過）或 `any`（指定人至少一人通過）；本批採 all 並明列 PM、行政兩方責任，不留預設待問。兩方不等於固定兩個唯一自然人：各方多人、同人兼任或任職空缺的解析及計票細則仍須核定。其他尚未設定規則的節點可存草稿及共同作業，但不得默認通過。

| 實體／欄位 | 契約 |
| --- | --- |
| node_review_rule_versions | 不可變規則版本、node/template、all/any（未決為未設定）、指定角色／人員解析規則、必備文件及前置條件、發布人及生效時間 |
| node_review_cycles | cycle UUID、案件／節點、規則版本、提交內容／文件版本 hash、發起人、狀態及物件版本；每次重新送審建立新 cycle，不重用已退回 cycle |
| review_role_snapshots／eligible_voters | 發起當時的 PM／行政等責任角色、解析出的穩定 person_id、可投票者、代理範圍、資格依據與時間；不能用可變人名當投票鍵 |
| node_review_votes／review_events | cycle、投票者、實際操作者／被代理者、同意／退回、理由、時間、冪等鍵、內容版本；相同 person 的重送不增加票數，保存全部歷程 |

`all` 僅在已核定且非空的指定人名單全數對同一 cycle 同意後成立；本批還必須檢查 PM 與行政兩方責任均滿足，不能只按票數湊滿。`any` 僅在已核定且非空名單至少一人對同一 cycle 同意後成立。兩者都必須通過文件／必填欄位、來源回寫核實、前置任務及凍結狀態等完成 gate；有同意票不等於可以繞過缺附件或遠端尚未儲存的 Input。名單解析空白或指定角色無有效人員時進待分派，不能採空集合全數同意。

發起後的內容及附件版本固定供審核；影響審核內容的修改使本 cycle 失效並重新送審，不把舊同意移植到新版本。有效退回以交易將 cycle 標為 returned，所有既有同意失去完成效力但保留稽核；修改後建立新 cycle，須重新取得當輪同意。

投票與完成判定在同一 DB 交易鎖定 cycle／節點版本，驗證投票資格及內容版本，寫入事件後重新計算 all/any，再最多一次執行完成狀態與 outbox。雙擊／重送按冪等鍵回原回執；同鍵不同意圖409。並發同意／退回由資料庫交易確定順序；已結束 cycle 的遲到票回409，不暗改結果。若已通過後需要退回，走明確的重開／退回命令、依權限另建cycle，不能回補一張票改寫已發生的下游操作。

快照保留歷史責任，不代表停權者仍可投票。每次投票重新驗證在職、角色與代理有效性；人員變動、代理到期、指定角色無人時標示資格待處理，不默默刪除名單降低 all 門檻，也不把新任人自動當已同意。具權限管理者可處理接替，保留前後快照與理由；接替時如何處理既有票、代理票代表本人或被代理角色、同一人兼任 PM 與行政是否算一人或兩個責任席位，列具體待核定規則，實作不得先假定。決定前相關歧義 cycle 不可完成。

這是工作台的節點審核事件，不是 Lark 原生審批 instance。兩者分開實體／狀態／回執；設計變更、展延等仍須原定外部審批。若節點還要求 Lark 審批，需同時滿足本地 all/any 與有效外部核准，不能一個節點同意票冒充 Lark 已核准。內部全員財務可讀及既有系統管理／超管權限設計維持；管理身分不會自動成為 eligible voter 或補出其他人的同意。

驗收新增：all 少一人不可完成、any 一名有效人可通過但缺文件仍阻擋、未設定模式／空名單阻擋、退回及改版後舊票無效、不同 cycle 不混票、重送不多票、並發同意／退回結果唯一、停權／代理到期拒票、人員接替留快照、同人兼職歧義未決不放行、本地節點通過不偽造 Lark 審批成功。

## 6. 同步防迴圈及版本生命週期

- 每次回寫保存目的 record＋欄位集＋值 hash＋write batch；後續讀同步識別為自身結果，更新來源快照但不再排同一寫入。
- 同編號多來源遇值衝突仍同案，但關鍵Input不能挑最新record直接寫；由來源映射選唯一權威目的，來源新增副本不擴張寫入範圍。
- 工程確認單編號修正、工項換版、設計變更作專用版本事件，更新關聯且保留舊文件／歷程；不得把案件主鍵改成新遠端record而失去資料。
- 来源被刪或無權讀分開處理，不直接重建同名record；只有確認遠端刪除且目的建立政策允許時才由明確恢復流程處理。
- Input值或文件改版不自動重新打開已完成任務；若影響已核准工項／期限，進設計變更或展延適用範圍。
- 稽核不寫token、secret、完整薪資內容；完整機密差異保存在受權限保護的版本資料，運維日誌只記識別與錯誤分類。

## 8. 查證門檻與真正未決

### 由實作團隊先查，不要求使用者記住技術ID

1. Meegle各節點真實Input定義與附件、目前欄位可寫型別、既有Base及Drive位置、來源多記錄的標记；整理逐欄映射與新表差異提案。
2. 最新官方Base寫入／Drive上傳、附件token、條件更新、idempotency/client token、大小及分片限制，建立端點契約與staging驗證；本稿不宣稱這些能力已存在。
3. 公司App的實際scope、資源授權、公司持有目錄、user/bot可行性與離職交接；沒有權限時提出具體最小授權差異。
4. 報價日期、回傳日期、PM日期、數字型確認單到期日的語意，以及是否已有正式發出記錄；先查看實際欄說明與少量樣本。

### 查完以具體方案請使用者裁定

- 目前尚未核定的每項必要Input／交付文件、完成gate與覆核者；已決的節點歸屬不重問。
- 沒有適用既有目的地時，核定新Input登錄表及公司受控Drive根目錄方案；若同案多來源無权威標記，選定可寫目的及內容衝突處置人，不重新問是否同案。
- 計價／請款／入帳／結算／結案由 PM 與行政共同同步處理、兩方皆通過才完成，以及內部全員可讀案件財務均已決，不重問預設模式或共同承辦歸屬。只核定具體寫入／核准人員及正式發出權，另核定各方多人／任職空缺、人員接替時既有票效力、代理代表方式及同人兼任兩職責的計票規則。
- 文件保留／刪除政策及重大衝突的裁定角色；第一版建議保留舊版、無自動遠端刪除。
