使用者已明確要求 Input 欄位存回 Lark 多維表格、檔案存回 Lark 資料夾，兩者均列入本版正式範圍。報價、日報與成本的來源同步維持讀取；新增的 Input 回寫走獨立欄位映射、權限、衝突與稽核流程，不取得對整張來源表任意修改的能力。人工日報配對與分派仍先存在工作台，不能因 Input 回寫授權就自動修改日報關係。Meegle 匯入後由哪一邊維護 SOP，列為審查決策，不能同時無規則雙向同步。

目前 280 個工作台案件由 280 筆報價紀錄建立，不代表有 280 個不同工程。使用者已確認「以編號為準，重複可能是不小心重複」，並進一步指定「以確認單的為準」：以工程確認單編號作為案件的業務識別基準，同一公司、同一工程確認單編號歸到同一案件，多筆來源記錄連到同一內部 project_id，不因來源 record 或報價編號不同而建立多案。報價編號為來源識別及搜尋欄位，不能取代工程確認單編號。不同確認單編號不因報價相同而合併；有明確設計變更關係時另存前後版本關聯。欄位字典核對實際確認單編號欄位及跨表關係，不混用編號體系。

尚未取得工程確認單編號的報價保留為待確認案件／接案紀錄，使用暫存內部 ID，仍可執行報價與 PM 前期工作，但不假定報價碼就是正式案號。取得確認單後依來源關係接續轉入／關聯正式案件，保留已有操作；一份報價對應多份確認單時保留明細關聯及分配，不複製整份金額加總。本次確認針對案件編號基準，不據此推定所有財務欄位均改採確認單數值。

只清除首尾／不可見空白等不具業務意義字元；保留編號前導零、連字號與分案後綴，不以模糊或前綴比對合併。缺編號記錄進待核對，不把所有空白歸為同案。相同編號資料一致時去重展示及計算；金額、工期或內容不同時仍歸同一案件，但標示欄位衝突，核對有效值前不任選最新記錄、不重複加總。已明確標示的設計變更保留同案版本與適用範圍，不當誤建資料刪除。原始來源與歷史操作保留，已建立重複案件以遷移對照合流，保護既有任務、文件、審批、連結及歷程。

## 4. SOP 全量盤點、對照與匯入

使用者已確認：工程確認單的工作項目直接對應到九大節點中的適用節點，並在節點內承接該工項的 SOP 子任務、預算、工天、日報及成果；不是只將整份確認單放在「確認單」節點。跨組工項保留同一来源，分別關聯各節點的執行工作與分配額，不重複計算整份工項金額。「確認單」節點管理確認單的製作、確認、傳遞與版本。

第一批歸屬已確認：業主提出報價需求、建立報價編號、提出報價並通知、報價單是否回傳、收到回傳單合約成立、通知業主報價成立、得標後聯絡業主，均留在「報價」。其中「得標後聯絡業主」可由 PM 負責。節點歸屬與執行角色分開設定，不能因負責人為 PM 就移入「PM 派工」。確認單正式發出後，指定 PM 接手成為案件主責並追蹤各組確認；確認單前已有的 PM 任務仍可執行。

第二批歸屬已確認：初次繳交確認單、確認單製作並傳遞各單位、外業確認單確認、內業確認單確認、確認單修正，均放「確認單」。外業／內業確認由各組負責人執行；核准後影響範圍的修正接設計變更。使用者明確選擇「確認單發出後，PM 接手追蹤各組確認」，不等各組全部確認。正式發出記錄版本、操作者與時間，須已有有效指定 PM；單純上傳或草稿不觸發交接，不自動完成各組確認任務，改版也不重複交接。逐項決策見 SOP_MAPPING_DECISIONS.md。

每個節點須有對應應上傳／交付資料清單，依 Meegle 實際內容盤點，再確認必填、條件適用、提交時間、負責角色與覆核要求。清單區分 Input、Output 與佐證，支援來源已存在文件的引用，避免重複上傳；跨任務引用同一文件仍須辨識適用案件、工項與版本。必要文件缺漏時依核定的完成 gate 提示並阻擋相應完成操作；哪些文件為必要尚未全部核定，不能自行替每個節點強制相同附件條件。每份文件保存 Lark 位置、版本、提交人、時間及關聯，後續改版保留舊檔追溯。

所有現行實際使用功能另建「原功能／來源位置 → 新功能位置 → 資料落點 → 權限 → 串接 → 驗收 → 缺口」清單，逐項核對，避免僅搬任務標題而遗漏資料區、附件、提醒、分支、審批及管理功能。

1. 先取得 Meegle 可讀空間、工作項類型、流程範本及資源庫清單；記錄已讀、無權限、失敗與不適用範圍。API 可取得範圍不足時，以唯讀後台補查。未遍歷範本清單，不宣稱「全量完成」。目前 Meegle CLI 尚未登入，連線為盤點前置條件。

3. 逐項對應業務、PM、確認單、外業、控制、圖資、報告、計價、結算。顯示名稱統一，後端穩定 key 不因改名而改變。
4. 對照表至少包含：原 SOP、原節點、新節點、適用案件／工項、每案／每工項／每批次執行粒度、角色、工作量、期限依據、輸入、交付驗證、相依、理由及審查狀態。

9. SOP 作業指引改版與業主設計變更分開；若影響核准範圍或期限才進相應變更／展延流程。不得因新增必要 SOP 自動重開已完成節點。

## 5. 營業額、成本預算與排程

- 實查報價欄位 ID、公式、單位、含稅／未稅、幣別、整案／部門／工項粒度及版本標記。歷史 metadata 顯示有部門預算成本及工天，可作查證入口，不能只憑欄位名稱認定計算意義。
- 金額以精確十進位及明確幣別保存；未取得為 null，真正零為 0；收入金額、預算成本、實際成本、工作量點數及工天分開。
- 整案金額只計一次；部門／工項分配是總額的分解，不與母層相加。顯示來源總額、已分配、未分配及超配；來源未提供分配時，不自動平均。
- 實際成本待確認成本單及明細計算、共用成本分攤與去重識別後接入。資料未完整時顯示涵蓋範圍，不提供誤導的零成本或最終盈餘。即使來源有值 0，也需區分已核實零值與測試暫填零值，保留核實狀態。
- 保存原始預算、核准預算版本及實際發生值；報價換版先展示差異，已執行案的核准基線不因同步被改寫。
- 確認單的「時間」先分成日期、工作天數、人天或里程碑。工天不能直接當期限，也不能在未有量能與開始條件時推算結束日期。
- 排程保存原基線、現行核准值、來源建議值及實際起訖。初排可依工作日曆、前置成果與人員量能生成建議，PM 核定後生效。
- 外業與內業允許按工項／批次並行，不能用整案單一目前節點取代。既有核准期限的變更仍走展延，核准未套用前沿用原期限。

## 6. 案件日報與關聯核對

案件設獨立日報頁籤，以日期排序，依部門、人員、工項及關聯狀態篩選；展示來源實際存在的內容、數量、點數、工時及附件，缺欄位明示。可從節點或任務查看相關紀錄。

配對優先採來源正式 record 關係及核定對照；案件主檔以同公司同工程確認單編號匹配。同確認單的多筆來源不再單獨造成案件層級歧義；只有報價碼時須經報價至確認單的可靠關係對應，不能直接當確認單編號。暫填確認單編號仍保留暫填證據標記。配到案件不代表已確認報價版本、工項或預算有效值；正式來源關係與確認單編號互相矛盾時進待核對。現有 1 筆暫填與 534 筆待核對是舊規則的同步快照，不能據此預告新規則配對數；遷移後重新驗證。

建立待核對佇列：顯示原始來源、缺少關聯原因、候選案件與依據；授權者選擇案件／工項、填原因、確認，保存操作者、時間、來源版本及前後值。可撤銷／改配，來源改動衝突時重新待核對，不悄悄保留過期配對。

日報與工項／任務採可多對多的證據關聯；如需分攤數量／成本，另有 allocation 明細及總額守恆驗證。不能把同一份日報或同一張成本單完整加到多個案件、人員和子任務。

日報只代表活動證據，不自動完成 SOP。下一工作日控制檢查仍依實際工作日期、案號和組別；來源不完整時顯示待確認，不直接判定未作業。

## 7. 案件搜尋與介面重整

- 案件搜尋涵蓋案號、名稱、業主／客戶及報價編號；支援部分字串、空白正規化與清除搜尋，不以近似結果自動合併資料。
- 結合負責人、部門、目前有效節點、狀態、期限區間及逾期篩選；多節點並行的案件可出現在多個節點篩選中。
- 後端先做權限過濾，再搜尋、排序、計數及分頁；使用 PostgreSQL 索引及依實測補字串索引。查詢參數可保存於 URL／個人視圖，返回列表保留位置；不得在 URL 帶敏感內容。
- 列表採清晰字級、穩定行高、適量留白與單一主要強調色。重要狀態同時有文字，不只靠顏色。減少重複外框、過小淺色文字及競爭按鈕。
- 案件詳情依序呈現案號／名稱、責任與期限、適權的財務摘要、九節點流程；下方以工項與 SOP、日報、文件、審批、歷程分頁。
- 任務統一詳情側欄：基本資料、輸入輸出、排程與人員、成果、留言與操作歷程。舊版本移至明確的歷史區，可追溯但不混淆現行待辦。
- 預算與排程以來源／核准／實際區分，缺值不畫成零。管理介面包括 SOP 範本、來源核對、人員／角色／交接、同步狀態與工作日曆。
- 先交付案件列表及案件詳情兩個代表畫面，由使用者審查後再擴展。維持繁體中文與現有九節點語意，支援鍵盤、焦點、讀取／空白／錯誤狀態及手機基本操作。

### 7.1 節點 Input 資料區與 Lark 回寫（已確認範圍）

使用者已確認「兩者都要：欄位回多維表格、檔案回資料夾」。Input 依 Meegle 實際節點的欄位、資料關聯及檔案內容建置，不能只用通用文字框代替；先盤點實際結構，不聲稱已取得完整 Meegle 資料庫定義。

- 欄位區：依節點呈現文字、數值、日期、人員、選項及關聯紀錄等來源實際型別，保留單位、必填、驗證與來源連結。公式／查找／系統唯讀欄只展示，不直接覆寫；影響核准預算、範圍或期限的欄位仍遵守審批規則。
- 檔案區：支援上傳、瀏覽、開啟 Lark 原檔及版本追溯。預設資料夾提案為「工程確認單編號／節點／Input」，再以子任務與版本連結索引，避免同一檔案複製多份；尚無確認單時使用暫存案件識別，之後更新關聯而不遺失檔案。
- 映射表：每個可寫欄位保存目的 Base／table／field ID、來源 record、案件／節點／子任務及版本；檔案保存 Lark folder/file token、檔名、大小、checksum、上傳人及狀態。目的表／根資料夾沿用適合的既有資源，無對應結構時提出具體新增方案，不能未查就自動覆寫原表。
- 儲存語意：可先保留本地草稿，再以明確「儲存至 Lark」操作送出；按欄位／檔案呈現草稿、排隊、儲存中、成功、衝突與失敗。只有遠端確認成功並記錄回執後才顯示已存回 Lark，部分成功須逐項呈現。
- 後端操作：寫入前驗證使用者對案件與欄位的權限、目的 record 身分、目前來源版本及預期值；不信任前端自帶 table／field／folder。目的資料已更新時顯示差異，不能無提示覆蓋。
- 並發限制：先查證 Lark 是否提供該端點可用的條件寫入／版本控制；不支援時採本系統對同 record 串行、寫前比對及寫後讀回檢查，仍明示外部使用者同時修改的競態限制，不宣稱跨系統原子鎖。
- 多步寫入：Base 與 Drive 不具本系統可保證的共同交易，採持久 job／outbox 與逐步回執；檔案成功但欄位失敗時可續傳關聯，保留未完成狀態。對不確定是否成功的請求先查核再重試，避免重複 record／檔案；不以失敗補償任意刪除遠端檔案。
- 長期授權：核對 Base 寫入、Drive 上傳及目標資源權限，使用受控公司應用／經核定身分，避免檔案與資料夾只依附某位離職員工。遠端檔案也須有正確存取範圍，不能靠工作台隱藏連結代替 Lark 權限。
- 稽核：留存操作人、代理人、來源與目的版本、欄位差異、檔案版本、時間、失敗原因及遠端回執；機密憑證不進記錄。回寫產生的來源變化以版本／雜湊辨識，避免同步來回迴圈。
- 驗收：包含正常儲存、型別錯誤、無權限、token 失效、限流、網路中斷、部分成功、重複送出、外部並發修改、來源刪除、檔案重名與版本、離職後資源仍可維護，以及 Base／Drive 真實讀回核對。測試使用隔離資源，試行後再啟用核定目的地。

## 8. 人員與權限的長期使用

使用者明確要求參考現有人員架構，新人入職後可一條龍持續使用、不修改程式碼。本版必須把人員、部門、職務、角色、案件範圍、代理及交接配置移到資料庫與授權管理介面；正常到職、調職、主管異動、離職不修改程式、環境變數或重新部署。系統整合憑證輪替等平台維運仍屬不同操作，不以此承諾任何外部設定都永遠免管理。

本輪已實查 Meegle「業務流程」角色清單，共 10 項且無下一頁：總經理、副總經理、專案經理、專案助理、業務經理、行政經理、外業經理、外業組長、內業經理、內業組長。這是工作項角色，不是完整公司組織樹或人員名單，不能據此推定任職人或上下隸屬。Meegle 此空間 team 清單返回 0，不能解讀為公司沒有部門；Lark 正式部門、員工及主管關係仍待授權可讀範圍盤點。職稱與系統權限分開，不將總經理等職稱直接等同系統超級管理員。

入職旅程：取得 Lark 身分 → 管理者確認在職／部門／職務 → 套用可維護的權限範本與案件操作範圍 → 設定主管及適用執行角色 → 檢查 App／Base／Drive 實際可用範圍 → 登入看見我的工作並可被派工。可從通訊錄同步的欄位自動帶入，未授權範圍明示並提供受控維護；依已核定政策，全員可讀案件財務，但不自動取得修改、核准或系統管理能力。

SOP 保存「職務／執行角色」而非固定某人。新案按有效角色任職對應人員，多名候選則由主管分派，無人任職則待分派；不任選第一人。主管換人只更新有效角色配置，新任務依新配置；既有任務依交接預覽保護人工分派與完成歷史。制度或部門更名不更改穩定角色 ID。

使用內部 person_id 作穩定主鍵，另存 tenant、Lark app／open_id／可用的其他平台識別映射，不以姓名或單一 App open_id 當永久人物主鍵。部門、人員在職狀態、職務與角色採有效起訖時間。

| 情境 | 正式行為 |
| --- | --- |
| 到職 | 同步／授權建檔，配置部門及案件範圍，預設最小權限；不能自動繼承同名離職者 |
| 改名／調職 | 更新現行資料；保留歷史 actor 與當時姓名快照；不自動把舊部門全部案件轉到新部門 |
| 請假代理 | 指定案件／任務範圍與有效期間；實際操作者及被代理者均留存；不額外擴張財務修改／審批權 |
| 離職／停權 | 阻止登入及後端操作、撤銷有效 session，停止新分派；歷史任務、文件、審批及姓名保留 |
| 工作交接 | 列出未結任務、節點責任、待審申請、代理與來源連線；逐批預覽新負責人、接受交接、完成回執 |
| 無接手人 | 放入待分派佇列通知管理者，不默認完成、不刪除、不分派給停權者 |
| 管理員交接 | 可配置至少兩名授權管理者；不把同步和系統維運綁在建立者個人登入 |

角色區分系統最高管理員、系統管理、SOP 維護、PM、節點主管、一般執行、財務操作及唯讀，採角色＋案件／部門範圍＋資源操作的後端檢查。最高管理員具有全系統調配權；所有有效公司成員可讀案件財務，修改及核准另控。搜尋結果、匯出與附件下載使用一致公司範圍及資料政策。停權與角色變更須在後續請求生效，不能只等 cookie 過期。

人員來源優先依 Lark 通訊錄可授權範圍設計事件＋定期核對；暫無 scope 時提供授權管理者的明確維護流程。未驗證的通訊錄能力不列為已串接。

## 9. 資料結構與後端

維持 React／TypeScript、FastAPI、PostgreSQL。核心業務拆出 workspace JSON，原始來源快照及可變範本內容可用 JSONB。採版本化資料庫遷移，不能依 create_all 取代 schema 升級。

| 資料群組 | 核心實體／關係 |
| --- | --- |
| 組織與授權 | organizations、people、external_identities、departments、memberships、role_bindings、delegations、sessions |
| 案件及來源 | projects、project_members、source_connections、source_records、project_source_links、quote_versions、confirmation_versions |
| 工項與 SOP | commercial_items、work_items 及商業／執行工項關聯、work_batches、nodes、sop_definitions、sop_versions、sop_rules、tasks、task_dependencies、task_assignments |
| 財務與時間 | budget_versions、budget_lines、allocations、cost_entries、schedule_baselines、schedule_changes、calendars |
| 日報 | daily_reports、daily_items、report_links、mapping_reviews；保留來源版本及人工決策 |
| 協作與審批 | approvals、approval_scope、approval_events、files、file_versions、comments、audit_events、handover_batches |
| 整合運維 | sync_runs、sync_cursors、jobs、outbox_events、webhook_receipts、idempotency_receipts |

所有公司資料有 tenant／organization 範圍；外鍵和唯一約束確保關係存在。來源以平台＋租戶＋Base／空間＋表／類型＋record ID 識別；案件以內部 UUID 作技術主鍵，以公司＋正規化工程確認單編號作正式案件業務唯一鍵，未取得確認單的待確認紀錄不共用空白唯一值。更正確認單編號需保留前後對照並檢查衝突，不能直接建立新案而切斷歷史。任務使用獨立穩定 ID，範本版本不改寫歷史。商業分項與部門填報工項分開，不能將後者當收入明細加總；案件依確認單編號去重，不代表同案合法工項也要去重刪除。

API 分離案件列表、摘要、節點／任務、日報、財務、文件、人員及管理功能；列表分頁，詳情按需載入。採物件版本鎖／衝突回應與請求冪等鍵，不再用整個公司 workspace 的單一版本讓不同案件互相衝突。業務狀態、事件及待送外部事件在同一交易保存。

為欄位及 API 建立型別／單位／空值／權限／錯誤契約。工作台仍負責流程管理，來源財務結算公式若由 V4 管理，僅保留可追溯快照與核對，不私自建立不同的結算算法。

## 10. 串接、同步與審批

- Zeabur 運行 Web/API 及背景 worker；初期以 PostgreSQL job 表及交易鎖管理工作，不先增加無需要的基礎設施。
- Lark connector 明確列每張表的欄位 ID、型別、關係、讀取身分及授權。背景讀取优先使用獲准且能讀目標 Base 的應用身分；不能假設現有使用者 scope 可直接變成 bot 能力。需 user 身分的功能具 refresh、安全儲存與失效通知。
- 同步採分頁完整性、欄位 schema 檢查、冪等 upsert、排程互斥、429／暫時錯誤退避重試及失敗佇列。只有成功提交後推進游標；失敗保留上一個完整快照與明確過期標示。
- 增量能力須實測來源支援；不支援時用受控全量＋內容雜湊差異。表或權限突然缺資料不能當成來源刪除；經完整核對確認刪除後封存來源，不刪執行歷史。
- Lark 審批配置真實定義與表單映射；送出保存案件、任務範圍、版本、申請人及本地冪等 ID，外部失敗可重試但不重複送單。
- 回呼驗證簽章／加密／租戶、去重事件並處理亂序；以授權 API 查核目前結果，另有定期補查。找不到對應案件或版本變動的審批進入待處理，不直接套用。
- 設計變更保留已確認的主管／業主證據及 Lark 內部審批並行；三線條件齊備仍需授權者明確套用。展延待審維持原期限。駁回、撤回、取消、重送與來源換版均有明確狀態機。
- 外部提醒另行設定收件範圍、觸發事件及去重；本輪規劃不實際發送訊息。服務錯誤不得顯示已送出或已核准。

## 11. 遷移、維運與正式部署

1. 建立独立 staging，使用去識別或隔離測試資料，不將 production token 複製給前端／測試附件。
2. 备份現有 DB、附件、schema 版本及檔案索引；建立 workspace JSON 至新資料表的可重入遷移工具、ID 對照及逐項對帳。
3. Dry-run 比對案件／任務／附件／留言／審批／歷程數量與關聯；檢查已操作示範 SOP，先列差異，不任意覆寫。
4. 試行階段用來源唯讀同步與一批授權代表案件；確認完整旅程後，安排短暫寫入維護窗口完成最後快照與切換，避免兩套系統同時寫入分歧。
5. 保留舊資料唯讀快照；回退計畫同時考慮 schema 和切換後新寫入資料，不能只回滾容器而丟失新紀錄。
6. PostgreSQL 與附件持久保存；備份送至不同故障範圍的存放位置，設定加密、保留期、失敗告警。正式上線前在隔離環境實際還原 DB＋附件並核對。
7. 記錄健康狀態、同步新鮮度、job 堆積、審批事件失敗、登入問題、儲存容量及備份成功；日誌不記 token、secret 或完整私密內容。
8. 暫定運維提案為每日備份、30 日保留、RPO 24 小時／RTO 4 小時；這是待成本與還原演練驗證的目標，不是已達成保證。業務若不能接受一天資料損失，改採更密集備份／可行的時間點還原方案。
9. 交付部署、回退、還原、金鑰輪替、App／管理員交接及異常處理手冊；正式環境移除匿名 demo 入口，示範留在隔離環境。

## 14. 需查證及需使用者裁定

### 我們先查，不要求使用者憑記憶回答

- Meegle 空間／範本清單、SOP 數量、角色、分支及原始附件可讀性。
- 報價預算與收入、確認單工天／日期、實際成本及其公式的欄位 ID、型別、樣本與版本關係。
- 同確認單編號重複來源的欄位差異與明確版本標記；確認單編號實際欄位、報價至確認單關係、日報缺關聯範圍及可靠識別路徑。案件同一性已依使用者指示以工程確認單編號為準，不再要求逐組裁定是否同案。
- Lark 通訊錄、Base 應用讀取、原生審批定義、事件訂閱與長期授權的實際能力。
- Meegle Input 的實際欄位／關聯／檔案結構、可沿用的 Lark 目的表及根資料夾、Base 寫入與 Drive 上傳／存取權限；確認哪些欄位唯讀或須審批。
- 目前 280 案中的人工操作資料，以及需要保留的個別指派／附件／歷程。

### 真正的業務決策，帶具體清單再確認

1. SOP 權威範本及未來維護位置；每案／工項／批次頻率、必要完成證據與發布人。
2. 新 SOP 對既有案件的採用範圍。建議預設：新案用核定版，舊案由主管依差異預覽選擇套用。
3. 報價／預算及確認單版本的核准基準、工天意義與來源衝突優先序。先查欄位，再提具體選項。
4. SOP 發布／日報改配／人員交接、財務修改與核准的責任角色。財務讀取已確定全體公司使用者開放，節點保留現名且行政承辦，不再詢問這兩項。
5. 無法自動配對日報的確認人；建議 PM／指定主管確認，保留核對證據，不自動改寫來源。
6. 正式試行案件與驗收人、備份保留／復原目標及資料保留要求。可先批准開工，再於相依階段完成決策。
