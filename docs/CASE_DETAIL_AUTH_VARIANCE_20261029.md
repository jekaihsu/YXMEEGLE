## Findings

The reproduced 5–19-second navigation tail is principally **after the application has finished sending small responses**. It is not an identity/session/token-refresh wait in the matched requests. This establishes an external delivery floor; it does not identify whether the responsible component is the kernel/host, Zeabur proxy, HTTP/3 transport path or Chromium network service.

One authenticated navigation on the instrumented `a5bf420` runtime took 18.85 seconds to show the expected SOP block and four tasks. Its first-screen request, ID `483fc0a26eb449dd82fcd504df8e132c`, took **12,329.9 ms in Chromium**, including **12,221.1 ms download**. The matching application log records **26,294 bytes / two ASGI body messages**, **56.1 ms through headers**, **58.2 ms through complete body production**, and **0.1 ms in ASGI send**. Identity was **28.5 ms**, transport/worker queue **2.5 ms**, DB pool **5.3 ms**, SQL **21.8 ms**, GC overlap **1.0 ms**, and observed request loop lag **0 ms**. There is no upstream HTTP span in this request. About **12.27 seconds** therefore remains after application completion. The timing comparison uses Resource Timing's response end, not JavaScript JSON parsing time.

Another shell request, ID `596ff5b82fa04fdc9425c8bf257327aa`, took **10,958.7 ms** in Chromium. The app completed **33,140 bytes** in **2,565.0 ms**, spending **0.1 ms** in send; **8,393.7 ms** remains outside that interval. Identity was 399.4 ms, queue 14.4 ms, DB pool 130.1 ms and GC overlap 819.3 ms. These are real application costs, but they do not account for the subsequent eight seconds. Across this instrumented series, the loop monitor's largest recorded lag was **769 ms**, with no event-loop lag above three seconds. This also limits a synchronous post-response logger/event-loop stall explanation.

The independent Mac health samples usually took roughly 0.1–0.3 seconds. That is a useful control, but does not isolate Chromium's HTTP/3 body-delivery path. No particular hosting component is blamed without evidence.

There is a **separate cold construction cost inside the application**. The first authenticated case read after boot on `a5bf420`, request `b3393c31a97a4969b86f58375ce30fa7`, spent 4,669.4 ms through headers, including 3,307.3 ms Lark HTTP and 1,316.8 ms snapshot-thread CPU; spans overlap. Identity was 59.9 ms and queue 8.3 ms. After boot roster warming on `99794f3`, the first cold read's request-path HTTP fell to **753.4 ms** and was identified as `nodecase`, but the total was still **4,774.6 ms**, with **1,278.8 ms snapshot CPU**, **944.8 ms SQL**, **314.2 ms GC overlap** and **1,704.8 ms storage wall time**. This is not reported as external-only or as a passing cold result.

## Changes

- `a5bf420`: every application HTTP response, including health, static files, redirects, 304s and handled/unhandled errors, gets an application-generated `X-Request-Id` and `Server-Timing`. Logs correlate the same ID/phases with byte count, body-message count, complete-body wall time and send time. Durations cover identity/roster, handler, JSON encoding, DB connection acquisition/query execution, upstream HTTP/rate/lock waits, GC overlap and loop lag. Concurrent/nested spans must not be summed.
- The hosted uvicorn entry point timestamps a message when the transport delivers its first bytes. `queue` extends from that point to the sync/async endpoint's start, including parser/task/thread-pool waiting. It cannot timestamp bytes waiting before the transport callback runs, or time in a proxy/kernel before application receipt.
- The opt-in `?perf=1` trace records the response request ID, server total, browser header wait, full response/parse time and their difference. Explicit 304s are logged too. Browser/server differences include transport and browser work, not only network latency. The collector additionally records Resource Timing download duration, transfer sizes and HTTP protocol.
- `99794f3`: shell responses use the existing bounded encoded single-flight cache and private HTTP revalidation. Every read still checks the current session/admission, viewer, workspace version, visibility and environment before a cached body or 304. Visibility edits without a version bump remain fenced. Mutation invalidation remains. No identity/session authorization cache was added: measured identity does not explain the missing seconds, and fresh revocation checks are retained.
- Cached response freshness ages advance from the origin's HTTP Date, without advancing `as_of` or converting an error/stale state to fresh. This covers browser-managed and explicit 304 reuse.
- Hosted startup warms the existing node-assignment roster/schema/application-token read cache in a background thread. The measured `99794f3` warmup completed in **2,281.4 ms** before authenticated QA. It persists no roster and changes no write-side fresh-roster checks or stale-admission bounds. Native case reads remain a possible cold upstream dependency.
- `77b6a8b`: shell weak validators ignore only clock age/server-time changes. Current source timestamps, refresh/error states, authority, visibility, features and build identity remain in the validator. An unchanged representation can validate even after the encoded cache expires, without reconstructing/retransmitting cards. This avoids treating a clock tick as a changed business payload.
- `c16ce48`: progress uses a **separate bounded 1 MB cache/executor**, leaving the existing 8 MB critical-read cache independent. A blocked-progress test requires shell completion within two seconds. This fixes a head-of-line wait exposed in the first progress-cache iteration: shell ID `14bde05307ff4d21aa769b96552e996b` spent 4,671.3 ms waiting/building in the shared snapshot queue despite only 110.7 ms snapshot CPU. Current source freshness and source-generation tokens join the key; generation is rechecked after retrieval, and source errors cannot reuse a healthy response.
- `1866359`: repeated progress projections now share the bounded encoded single-flight cache, gated by current session/viewer, workspace version, visibility and report-snapshot status/timestamp/staleness. A build rechecks identity. Deployments without a ready index keep the uncached path. Tests verify unchanged reuse, authorization/visibility revocation, and new report values replacing a cached result. This removes repeated case capture/projection work that previously continued behind rapid navigation.

The intermediate `99794f3` series already reduced shell body responses from **32/32 to 11/32**, with **21 empty 304s**, and shell response bytes from **1,060,329 to 417,230** (60.6% less). Its shell server p90 fell from 2,561.2 to 1,083.6 ms. These are observations in changing live windows, not a controlled claim that every latency difference is caused by the patch. The final validator avoids additional clock-only retransfers.

Percentiles use nearest rank.

Requested gaps are 0, 1, 2, 5, 10, 20, 30 and 60 seconds; early runs repeat immediately. Live sources/roster refresh during the sample. Initial warm-series cache misses after idle are retained, rather than silently excluded. The two series' 192 completed session/shell/first-screen requests all matched server logs by ID.

Additional `99794f3` samples include five fresh tabs and ten project-list navigations. Fresh tabs provide new JavaScript contexts in the authenticated Default profile; they **share its cookies and HTTP cache**. A separate empty authenticated browser profile was not available through the shared preview tooling, so these are not claimed as strict empty-cache browser-context measurements. First-post-deploy server-cache misses are reported separately.

An earlier exploratory series used a different 37-task case: 31 attempts, 26 completed, five censored by the initial collector deadline. It reproduced the long tail but is not used as a like-for-like case comparison. ## Open items and stopping condition

The measured 5–19-second tail is located beyond ASGI complete-body send; escalation needs the hosting/transport team to trace the representative request IDs against proxy/host logs, ideally comparing HTTP/2 and HTTP/3 with equivalent authenticated response bodies. Application timing alone cannot name the exact external component. No infrastructure settings, plan, worker count or paid action was changed.

Application work remains: post-boot first-screen capture can still exceed three seconds, and sequential session/shell/first-screen work can push warm SOP p90 above two seconds even when each read is faster. Cold native-case reads, snapshot capture/SQL and serialization are measurable contributors. These should be optimized separately after the delivery path is investigated; they are not hidden inside an external-only claim. Strict empty authenticated browser-context QA also remains open. This handback uses the user's alternative stopping condition: per-request proof of the external remainder, with unmet targets and internal remainder explicitly retained.

Raw local evidence is ignored under `.runtime/case-detail-perf/variance-*`: navigation captures, full request-ID correlations, runtime logs, exact-SHA health windows, deployed-file verification, hook output and frontend checks. This document retains the material measurements and representative IDs for PR review.
