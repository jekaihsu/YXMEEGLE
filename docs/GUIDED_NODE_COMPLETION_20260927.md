# 大節點逐項完成與阻塞處理

使用者要求：點完成大節點時，直接打開未完成的小任務，逐項補齊成果並快速處理；不能只留下錯誤訊息。另核定跳過節點需 PM 與該組主管共同核准，財務與結案保留既有雙方確認與結清條件。

## 已實作

- 未完成節點皆可開啟檢核視窗，包括無執行權者及暫停節點；任務開始、完成及最終送交仍各自檢查角色。
- 視窗直接顯示實際任務說明、Input、負責人與成果欄。待開始任務先明確按「開始此任務」，再「完成並前往下一項」。逐筆保存，沒有一鍵假完成。
- 成果檔案與連結可在同一流程加入，預設 Output；暫未送出的成果文字保留於同一案件／節點頁面。
- 非負責人只能檢視；提供責任與交接入口。暫停及前置成果未完成時，提供對應處理入口。
- 全部必做任務完成後回到實際檢核清單。缺交付、Input、確認單、期限衝突、財務或變更，可直接開對應頁面，並可「返回逐項完成」。
- 最終操作叫「送交節點確認」。API 建立待確認輪次後，明示「待指定人員確認」，不把待審說成完成。
- 正式變更／展延能力未就緒時，顯示 Lark 送審待設定、只保存草稿並停用送出；示範操作仍明確標為模擬。
- 已暫停任務增加案件關聯審批入口；成果批次缺技術佐證時增加各技術節點交付確認入口。
- 節點跳過提供獨立草稿／共同核准／PM 套用流程；顯示核准跳過而非任務完成。後端契約與驗證由另一 agent 負責。

## 實際驗證

使用 `http://127.0.0.1:8791` 的隔離示範工作區、獨立瀏覽器 `redesign20260927`，沒有寫入正式 Lark 或正式案件。

`quick-node-review.js` 的十項驗證通過：

1. 點完成節點直接打開第一項未完成任務。
2. 非任務負責人成果欄唯讀。
3. 無權限時可進責任與交接。
4. 三項任務逐筆完成後自動回到節點檢核。
5. 缺交付資料時送交按鈕不可操作。
6. 缺件入口直達實際交付頁。
7. 可以返回逐項完成流程。
8. 390px 手機沒有整頁水平溢位。
9. API 讀回三項任務皆 completed，成果內容逐筆保留。
10. 大節點仍為 in_progress，沒有被假標完成。

另以既有 API 在示範區提交、主管覆核明確標示的虛構佐證，再透過 UI 送交節點確認：實際回讀 review.status = pending，node.status = in_progress，画面顯示「小任務成果已保存，節點尚未完成」。

驗證途中發現 hash 路由會丟棄新增的 `section`／`completion`，造成返回入口消失；已修正 `api.ts` 並重跑上述十項全部通過。路由亦支援 `approval` 以開啟指定申請。

## 節點跳過實測補記

新版後端獨立服務 `http://127.0.0.1:8792`，同樣僅使用隔離示範資料：

- 初次缺少組主管時，實際送審按鈕不可操作；透過正式角色設定 API 指定示範主管，再撤回舊草稿建立新版本。
- UI 建草稿 → 送出測試審批 → PM 本人投票後仍 pending → 切換組主管本人核准 → 組主管不能套用 → PM 明確套用。
- 最新申請實際回讀 applied、節點 approved_skipped、兩票來自不同 actor，小任務仍 pending 並保留原成果狀態。
- 八項斷言全部通過，390px 手機無整頁水平溢位。
- 一次中途驗證選到了最早的舊撤回草稿，使斷言失敗；已改依版本讀取最新申請，並在另一個未演練案件重跑完整雙人流程，全數通過。

證據：[桌面核准跳過](../output/playwright/node-skip-applied-desktop.png)、[手機核准跳過](../output/playwright/node-skip-applied-mobile.png)。腳本 `node-skip-review.js` 會操作指定隔離示範案件，不能對正式工作區執行。

上述是本機後端與真實瀏覽器的測試模擬，不代表已送往 Lark 原生審批。
