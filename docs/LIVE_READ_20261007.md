# 即時讀取（live read）說明 2026-10-07

本文件描述 `backend/live_read/` 的實際行為，名稱、預設值與範圍皆取自程式碼（`config.py`、`routes.py`、`status.py`、`coordinator.py`、`client.py`、`admission.py`）。規劃見 `/tmp/yx_read_plan.md`（非 repo 文件），審查結果見 R1–R4；未經實測的項目列在第 9 節，不當成已驗收。本功能**只讀 Lark，不寫回**。

## 1. 是什麼

旗標 `LARK_LIVE_READ_ENABLED=true` 時，三個 Lark 資料集（來源 `sources`、人員名冊 `roster`、班表 `attendance`）改由 web 服務在使用者開頁時按需讀取（過期才讀、同一時間只有一個讀取、其餘共用結果），每個回應附 `freshness` 區塊標明資料時間。旗標關閉（預設）時，行為與舊版完全相同：worker 背景計時同步，不依賴本功能。

## 2. 架構摘要

- `RefreshCoordinator`（`coordinator.py`）：每個資料集一把存於 `source_caches` 的租約列（id `live:<workspace>:<dataset>`），以 revision 比對（CAS）搶佔；同進程以鎖與 future 合併請求；執行緒池 2 條，名冊另有專用 1 條與 1 個名額，不被來源／班表佔滿。寫入工作區前會再次以租約圍欄檢查，租約遺失則整次不提交。
- `LiveLarkClient`（`client.py`）：唯讀 HTTP 邊界。只接受 application 身分（需 `LARK_WORKER_IDENTITY=application`），不跟隨轉址，只允許 GET 白名單（Bitable 應用、`contact/v3/users/batch`、`attendance/v1/shifts/{id}`），POST 僅 `records/search` 與 `user_daily_shifts/query`；薪資（capability）Base 的寫入仍由 `capability_write_policy` 阻擋。
- 速率與重試（`rate_limit.py`、`token_cache.py`）：每進程一個令牌桶（容量 1，每秒上限 `MAX_RPS`）；每次請求最多 3 次嘗試；整次刷新預算 45 秒；等待時間優先採 `x-ogw-ratelimit-reset`，其次 `Retry-After`，否則 1／2／4 秒（上限 30 秒）；429 與 `99991400` 至少等 1 秒並讓整個進程的令牌桶一併退避；可重試碼為 `99991400`、`1254290`、`1254607`；`1254302` 或 401／403 視為權限不足（`blocked`），不重試。tenant token 依應用／組織共用快取，剩餘不足 35 分鐘時會重取，但 Lark 在剩餘 ≥ 30 分鐘時回傳同一個 token，故同一 token 至多每 60 秒重取一次。
- 資料集刷新器（`datasets/`）：沿用既有 `SourceSyncService`、`PeopleDirectoryService`、`AttendanceScheduleService` 的授權、政策與快照驗證，只換成 live 用戶端。來源 9 張表視為一個單位（完整快照才提交）。來源內容指紋（`fingerprint.py`，含表對映、欄位結構，排除附件簽名網址）未變且工作區投影一致時，不寫工作區。
- 名冊准入（`admission.py`）：見第 6 節。

## 3. 環境變數

由 `LiveReadConfig.from_env` 解析；非數字、NaN、無限大一律退回預設值，數值再套用下限／上限。除 `LARK_BITABLE_RECORDS_API` 外，皆以 `LARK_LIVE_READ_` 為前綴。

| 變數 | 預設 | 範圍（clamp） | 說明 |
|---|---|---|---|
| `LARK_LIVE_READ_ENABLED` | `false` | 僅字串 `true`（不分大小寫）為開 | 總開關。另需 `LARK_WORKER_IDENTITY=application`，且工作區非 `demo-`／`test-` 才實際啟用 |
| `LARK_LIVE_READ_SOURCE_TTL_SECONDS` | 旗標開 60；旗標關 300 | ≥ 30，無上限 | 來源資料集軟 TTL；旗標關時也是舊 worker 的最短間隔 |
| `LARK_LIVE_READ_ROSTER_TTL_SECONDS` | 旗標開 60；旗標關 300 | ≥ 30，無上限 | 名冊軟 TTL；旗標關時同上 |
| `LARK_LIVE_READ_ATTENDANCE_TTL_SECONDS` | 300 | ≥ 60，無上限 | 班表軟 TTL；旗標關時也是舊 worker 的最短間隔 |
| `LARK_LIVE_READ_MAX_RPS` | 5 | 0.01–10 | 每進程對 Lark 的請求速率上限 |
| `LARK_LIVE_READ_BLOCKING_TIMEOUT_SECONDS` | 10 | ≥ 0.01，無上限 | 需等待結果的呼叫（准入、手動 `wait`）最長等待 |
| `LARK_LIVE_READ_LEASE_SECONDS` | 120 | ≥ 60，無上限 | 租約長度，須大於單次刷新（45 秒預算＋寫入） |
| `LARK_BITABLE_RECORDS_API` | `list` | 僅 `list` 或 `search`，其他值退回 `list`（`backend/sources.py` 另對非法值回 503） | 紀錄讀取端點：`list`＝每頁 200（官方標為歷史接口）；`search`＝每頁 500、約少 40% 呼叫。切換前須在 staging 驗證連結欄位格式 |
| `LARK_LIVE_READ_TRANSPORT` | 未設 | 僅 `deny` 有意義 | 測試／驗收用：設 `deny` 時 live 用戶端拒絕任何真實網路請求。正式環境不要設 |

相關但非本功能新增：`LARK_WORKER_IDENTITY`（須 `application`）、`LARK_WORKER_ORGANIZATION`（背景／live 只服務此 tenant）、`LARK_SOURCE_MAX_PAGES`（1–100，預設 50）。TTL 變數在旗標關閉時也影響舊 worker（見第 8 節）。

## 4. 端點

- `GET /api/live/status`：任何已登入者；回 `{"freshness": …}`，`Cache-Control: no-store`，不呼叫 Lark。示範／測試工作區 `enabled=false`。
- `POST /api/live/refresh`：body `{"datasets": ["sources"|"roster"|"attendance", …]（1–3 項）, "wait": false, "force": false}`。
  - 僅限旗標已啟用的正式 Lark 工作區，否則 403。
  - `force=true` 或含 `roster`：需與舊手動同步相同的資料同步權限，否則 403；`force=true` 另寫一筆稽核 `live_refresh`。
  - 非 force 的 `sources`／`attendance`：任何已准入者皆可（等同開頁，受 TTL 與 30 秒錯誤冷卻限制）。
  - 回應：`200`＝全部已新鮮（或 `wait=true` 且完成）；`202`＝已啟動或進行中；`409`＝已有刷新持有租約（含 force 時有資料集正在刷新）；`502`＝讀取失敗或 `wait=true` 未達新鮮，內含 `freshness`。
- 既有端點的變更（旗標開啟時）：`GET /api/workspace`、`GET /api/sources` 先以非阻塞方式觸發刷新並回傳 `freshness`；`POST /api/sources/sync`、`POST /api/people/sync`、`POST /api/attendance/sync` 改委派協調器（`wait` 且 `force`），權限與回應形狀不變並附 `freshness`；`GET /api/admin/runtime-health` 的名冊狀態改看 live 名冊並新增 `live_read` 區塊（含 `queue_depth`）；OAuth callback 與准入見第 6 節。旗標關閉時 `freshness.enabled=false`、各資料集 `unconfigured`，工作區仍多帶 `freshness` 並多幾次 DB 讀取，不是逐位元相同。

`freshness` 形狀：`{server_time, enabled, datasets:{sources|roster|attendance:{as_of, fetched_at, changed_at, age_seconds, ttl_seconds, status, last_error, lark:{calls,retries,duration_ms}}}}`；`roster` 另有 `hard_max_age_seconds: 900`。`as_of`＝該次 Lark 讀取**開始**的時間（台北時間 ISO 8601）。`last_error` 只會是固定字串 `Lark refresh failed`。**公開輸出刻意不含** `fingerprint`、`changed_at`、`error_code`（R1 MINOR-2 修正；見第 9 節的影響）。

## 5. 新鮮度狀態與畫面意義

| status | 判定 | 畫面（`DataFreshness` 晶片） |
|---|---|---|
| `fresh` | 有 `as_of` 且年齡 < TTL，無錯誤 | 「Lark 資料 hh:mm:ss（N 秒前）」；前端會在 TTL 後依本機時間降為 stale，不需伺服器請求 |
| `stale` | 有 `as_of` 但年齡 ≥ TTL | 加註「資料待更新」；下次開頁觸發重讀 |
| `refreshing` | 租約未過期 | 「更新中…」，每 15 秒輪詢 `/api/live/status` 至結束 |
| `never` | 從未成功讀取 | 「正在讀取 Lark 來源…」 |
| `error` | 最近一次刷新失敗 | 「Lark 暫時無法讀取，顯示 N 分鐘前資料」＋重試按鈕；保留上次成功資料 |
| `blocked` | 授權或資源權限被拒（`1254302`、401／403） | 「Lark 權限不足（1254302），請聯絡管理員」 |
| `unconfigured` | 旗標關、示範／測試工作區、非 application 身分，或該資料集無刷新器 | 示範顯示「示範資料」，其餘「尚未設定」 |

優先序：有錯誤則 `error`／`blocked`；租約未過期則 `refreshing` 蓋過其他。錯誤後 30 秒內不會自動重試（冷卻）；`force` 不受冷卻限制。

## 6. 失敗行為與 900 秒名冊規則

- **來源與班表（顯示用）**：stale-ok。Lark 慢或失敗時照舊顯示上次成功資料，頁面標示年齡；單次刷新超過 45 秒預算即失敗；失敗不清空案件。協調器讀取失敗時，顯示端點退回快取內容而非 500。
- **名冊（權限用）**：硬上限 900 秒（`production_access.DIRECTORY_MAX_AGE_SECONDS`，未改）。准入時（`ensure_roster_for_admission`）：
  - 該人名冊戳記年齡 < 名冊 TTL：不讀 Lark。
  - 年齡 ≤ 900 秒（含邊界）：非阻塞觸發刷新，繼續使用舊名冊。
  - 年齡 > 900 秒或未知：阻塞等待（最長 `BLOCKING_TIMEOUT_SECONDS`）一次刷新，同時間的請求共用同一次，且受 30 秒錯誤冷卻；讀取失敗＝維持原拒絕（403「公司名冊已逾15分鐘未核實」）。例外：可走維修入口的 bootstrap 管理員與公司管理員授權者不阻塞（以非阻塞觸發）。
  - 准入函式的回傳值**從不**直接放行；一律重新載入人員後再跑原本的 `require_access`，故停權、公司管理員授權與 bootstrap 復原語意不變。
  - OAuth callback：名冊超過 TTL 時等待一次刷新，但失敗不直接拒絕，仍交由 `require_access(..., allow_recovery=True)` 決定（R1 MAJOR-1 修正）。
- worker 即使停止，三個資料集仍可由 web 讀取；worker 仍須運行以處理通知、Input、Drive、原生審批輪詢與請假代理刷新。
- 示範／測試工作區與非 application 身分：零 Lark 呼叫。

## 7. 以旗標回滾

1. 將 `LARK_LIVE_READ_ENABLED` 改為 `false`（或移除）並重啟 web 與 worker。
2. worker 立即恢復來源／名冊／班表三個舊計時（間隔回到 300 秒預設）；協調器回報 `unconfigured`；准入不再呼叫 Lark；手動同步路由回到舊分支。
3. 不需資料回滾：`source_caches` 內 `live:*` 列會被舊程式忽略；`PersonRow` 與工作區形狀未變。
4. 舊計時程式碼尚未刪除（計畫中的 T12 未執行）；T12 之後旗標回滾即失效，需重新部署前一版。
5. 回滾後名冊最久可能已超過 900 秒：舊 worker 恢復同步前，一般同事會被擋下，bootstrap／公司管理員仍可走維修入口手動同步。

## 8. 旗標關閉時的行為

`run_due` 的最短間隔現在由 TTL 設定決定：來源與名冊預設 300 秒（旗標關時），班表 300 秒，故預設與舊版一致（每五分鐘）。若設了 `LARK_LIVE_READ_*_TTL_SECONDS`，旗標關閉時同樣生效（下限 30／30／60 秒），可能使舊 worker 比五分鐘更頻繁。工作區設定 `source_sync_seconds`（預設 300）只是舊設定欄位，驗證時要求不可變更，**不代表實際間隔**。

## 9. 已知限制與未驗證項目

已知限制（依 R1–R4 審查與程式現況）：

- 名冊健康（runtime-health）依協調器的整體名冊時間，不是逐人戳記；個別人員可能已超過 900 秒而該區塊仍顯示 ok，准入仍以逐人戳記為準（R1 MINOR-5，已決定不改）。
- 白名單允許任何 Bitable app token 的讀取（含薪資 Base）；寫入仍被擋。尚未依設定來源縮小讀取範圍（R1 MINOR-5，已跳過，需另行審查相容性）。
- 單次 `search`／`list` 端點的連結欄位格式差異未在真實資料驗證；`list` 仍為預設。
- 目前來源 9 張表為單一單位，任一表失敗則整次失敗；未做逐表合併。
- `scripts/workbench_cloud_setup.py` 的 deploy 使用 Windows 的 `zeabur.cmd`；在 Mac 上部署前需先改為跨平台（未改，本任務僅文件）。
- 未確認 `backup_reconcile.py` 是否容忍 `source_caches` 中新增的 `live:*` 列（原計畫列為 T11 檢查項；本次 grep 備份相關 Python 未見對 `live:` 的特殊處理，行為未實測）。
- `LARK_LIVE_READ_TRANSPORT=deny` 為測試鉤子，不是營運開關。

未驗證（未對真實 Lark 或 Zeabur 呼叫，所有資料來自程式碼閱讀與單元測試）：

- 真實 Base 上的呼叫量、延遲、與 429 行為；staging 全流程與瀏覽器驗收未做。
- 附件欄位在連續兩次讀取是否產生相同指紋（已去除簽名網址參數，未以真實資料確認）。
- 公式欄位重算是否更新 `last_modified_time`（不影響內容指紋，內容雜湊為準）。
- 班表 `user_daily_shifts/query` 的頻率限制（官方文件未載明）；班別詳情 50 次／秒僅見於 Feishu 鏡像，Lark 頁未列。
- Lark `search` 預設 `page_size` 是否為 20（Feishu 為 20；Lark `.md` 僅列最大值）。
- 目前各表實際筆數（最近記錄 2026-10-01 為 2,605 筆）；呼叫量估計隨筆數線性增加。
